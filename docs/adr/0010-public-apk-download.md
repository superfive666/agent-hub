# 0010. APK 由 hub 自己分发：公开的 `GET /download`，产物不进 git

- **状态**：已接受
- **日期**：2026-08-30
- **关联**：[ADR-0009](0009-android-native-compose.md) · [部署](../08-deployment.md) §5.5

## 背景

[ADR-0009](0009-android-native-compose.md) 的 Android 客户端要发到用户手上。
这个平台只有一个管理员、装在自己的物理机上、agent 是自助接入的 ——
上应用商店（审核、开发者账号、包名归属）的成本远高于收益。

## 决策

### 一、`/download` 公开，不需要登录

**装 app 的那一刻用户手上还没有会话**，而他很可能正是想在手机上登录才来装的。
挂在鉴权后面就成了「要先登录才能拿到用来登录的东西」——
和 [`/api/join`](../../agent-hub/internal/api/join.go) 必须公开是同一类理由。

这不构成信息泄露：APK 是个**空壳客户端**，不含任何实例数据，
hub 地址和账号都是用户装完自己填的。同一份包可以发给任何一台 hub 的用户。

### 二、路径就是 `/download`，同时保留 `/api/download` 同义词

`/download` 是对外的正式地址 —— 用户会直接在手机浏览器地址栏里敲它。

但它**不在 `/api/` 下**，而 [部署](../08-deployment.md) §5 的反向代理只把
`/api/*` 与 `/healthz` 转给 hub。所以：

- 部署文档 §5 的 Caddy / nginx 配置**必须显式加上这条路径**；
- 同时在 hub 上把 `/api/download` 注册成同一个处理器。

第二条是给还没改过代理配置的部署留的。少了它，老配置下 `/download`
会被静态站接走，用户下到一个改名叫 `.apk` 的 `index.html` ——
安装器只说「解析包时出现问题」，**没有任何线索指向反向代理**。
这个失败模式已经在 `/api/join` 上被记过一次，不重复踩。

### 三、拿不出包时是 503，不是 404

没配 `ANDROID_APK_PATH`、或者配了但 CI 还没把产物放上来，都返回

```json
{"code":"apk_unavailable","retryable":true,"retryAfter":300,"message":"…"}
```

**404 的意思是「没有这个端点」，会把运维引去查代码**；真实情况是端点在、
只是部署没做完。两者要查的地方完全不同。

配套一个公开的 `GET /download/meta`（`{available, version, sizeBytes, updatedAt}`），
控制台靠它决定按钮长什么样 —— 没包时是禁用加说明，而不是一个点下去
吐 JSON 错误的按钮。**没包在 meta 这里不是错误**，是 `200` + `available: false`：
回 503 的话前端得把「暂时没包」和「hub 挂了」当成同一件事处理。

### 四、产物不进 git，由环境变量指路

`ANDROID_APK_PATH` 指向宿主机上的一个文件，CI 构建完放过去。
十几 MB 的二进制，每发一版往仓库里塞一份，一年就是几百 MB 的死重量。

**启动时不校验这个文件是否存在。** 校验会让「先起服务、再发第一个版本」
这个正常顺序变成启动失败。

## 备选方案

| 方案 | 为什么没选 |
|------|-----------|
| 上 Google Play | 审核周期、开发者账号、包名归属，对一个单管理员的自建实例是纯负担 |
| APK 提交进仓库 | 每版十几 MB 进 git 历史，且 clone 代码的人并不需要它 |
| `/download` 302 到 GitHub Release | hub 不用碰文件，但内网 / 无外网的部署直接不可用 —— 而"装在自己物理机上"正是这个平台的部署形态 |
| 挂在 `requireAdmin` 后面 | 「要先登录才能拿到用来登录的东西」 |

## 影响

- 反向代理配置多一条路径，**升级已有部署时要一起改**，否则下载会静默地
  返回 index.html。部署文档 §5.5 的验收步骤里第一条就是查 `Content-Type`。
- `docker/compose.yaml` 把宿主机的 `release/` 只读挂进 api 容器的 `/srv/release`。
- 发版是**原地替换同一个路径**，所以响应带 `Cache-Control: public, max-age=0,
  must-revalidate`，不能让中间层拿旧包顶新包。文件名里的版本号来自
  `ANDROID_APK_VERSION` —— 忘了改的话用户下载目录里两个版本同名，
  这是唯一一个「不改也能跑、但事后很难查」的地方。
- 用户需要允许「安装未知来源的应用」。这是自建分发绕不开的一步。

### 什么情况下重新审视

如果将来要发 iOS，或者用户规模大到需要灰度/回滚，那时 `/download`
这种「一个文件顶一版」的模型不够用，应该换成带版本清单的更新端点。
现在不预付那个复杂度。
