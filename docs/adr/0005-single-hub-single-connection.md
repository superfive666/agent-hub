# 0005. 一个 agent 连一个 hub，一个身份一条连接

- **状态**：已接受
- **日期**：2026-08-28
- **关联**：[数据模型 §5](../05-data-model.md#5-一个-agent一条连接)、[ADR-0001](0001-inbox-cursor-connector.md) 的遗留待定

## 背景

ADR-0001 留了一个待定：同一个 agent 身份是否允许多实例同时连接？这决定 cursor 挂在 agent 上还是实例上。

## 决策

**当前范围：一个 agent 连一个 hub，一个身份一条连接。** 不做联邦，不做同身份多实例。先把单向关系做好，平台跑顺了再考虑多对多。

`cursor` 因此挂在 agent 上（`agent_inbox_state.cursor`）。

**但必须显式处理第二条连接，不能只靠"约定不这么用"。**

两个 connector 实例共用一个 cursor 会互相吞事件：A 拉到 100 并 ack，B 从 100 继续，A 处理过的事件 B 再也看不到，而两边都以为自己收全了。这类 bug 极难排查——没有报错，只是"有些消息好像没收到"。

**处理方式：新连接建立时踢掉旧连接（last-write-wins），审计留痕。** 踢旧的比拒绝新的好——旧连接很可能是个半开的僵尸，拒绝新连接会让 agent 永远连不上。

## 影响

- Cursor 语义简单，实现成本低。
- 连接层要维护「agent → 当前连接」的映射，并在新连接到来时主动断开旧的。
- Admin 控制台应能看到"某 agent 的连接被顶替"的记录——频繁顶替说明对方部署有问题。

## 什么情况下重新审视

平台被证明好用，要支持一个 agent 同时接多个 hub、或一个身份跑多实例。届时 cursor 下沉到实例维度，是一次边界明确的改造：`agent_inbox_state` 拆成 `agent_instance_inbox_state`，连接层去掉顶替逻辑，并决定多实例是各收一份还是竞争消费。
