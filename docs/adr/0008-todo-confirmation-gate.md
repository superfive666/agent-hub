# 0008. Todo 的用户确认闸门与处理步骤

- **状态**：已接受
- **日期**：2026-08-29
- **关联待决项**：[需求 §1 待定](../01-requirements.md#待定)「方向确定、开始工作由主 agent 自己声明，还是需要用户点确认？」

## 背景

原设计里，主 agent 收到 `todo.assigned` 之后自己决定什么时候开工：先在 thread 里问几句，
觉得清楚了就声明 `start_work`。需求 §1 的待定项写着「倾向：主 agent 自己声明，用户可打回」。

实际用下来这条倾向不成立。一条 todo 的正文是人临时敲出来的几句话，
里面几乎必然有没写出来的前提；agent 读完不觉得有歧义，是因为它已经**自己补了一套假设**，
而这套假设不会出现在 thread 里——它只会出现在交付物里。等到交付出来才发现理解偏了，
浪费的是一整轮工作，而且返工时那套错误假设往往还在。

「用户可打回」是事后补救，代价发生在最贵的时间点。需要的是一个**事前**的闸口：
让 agent 必须先把疑问摊到 thread 里，人看过、点头，才允许它动手。

约束：

- 不能把提问也挡住。未确认阶段恰恰是需要密集来回的阶段。
- 不能依赖通知通道的可靠性。放行信号丢了等于这条 todo 静默卡死（CLAUDE.md 的第三条前提）。
- 重复放行不能产生重复的记录或事件——控制台上的按钮会被点两下。
- 要能在已有数据的库上升级。

## 备选方案

| 方案 | 优点 | 代价 |
|------|------|------|
| **A. 不做闸门，靠 skill 引导 agent 自觉先问** | 零改动；agent 侧灵活 | 靠自觉的规则等于没有规则。skill 是给 agent 读的建议，不同 runtime 遵守程度差别很大，而这条规则的失效成本是一整轮返工 |
| **B. 加一个 `awaiting_approval` 状态，卡在状态机里** | 概念上和现有 5 个状态一致，前端不用认新字段 | 状态会被反复推来推去（澄清 → 进行中 → 打回 → 进行中…），每加一个状态都要重新回答一遍「从这里还能不能开工」。而「有没有被人确认过」只发生一次且不可回退，编码进状态机是把一次性事实塞进了一个循环结构 |
| **C. `todo.confirmed_at` 时间戳 + agent 侧状态推进的硬校验**（选中） | 判据是数据本身，只有一个答案；顺带记下了谁在什么时候放的行（审计要的正是这个）；对状态机零侵入 | 前端要多认一个字段；升级后历史 todo 全部变成「待确认」 |
| D. 每条 todo 强制一轮「澄清 post + 人回复」才解锁 | 不需要新字段 | 「人回复过」不等于「人同意了」。人可能回的是「我再想想」 |

处理过程的记录方式同样有两个选项：

| 方案 | 优点 | 代价 |
|------|------|------|
| **E. 复用 `post`，靠约定格式或标记区分** | 不加表 | post 是「说了什么」，写完不改；进度是「做到哪一步了」，要能从 pending 改成 done。混在一起要么 post 长出一堆只有一半行会用的字段，要么「第 3 步现在什么状态」得扫正文猜 |
| **F. 新表 `todo_step`**（选中） | 结构化、可改状态、可关联到具体发言（`post_id`）；控制台能直接画时间轴 | 多一张表；seq 分配要处理并发 |

## 决策

**选 C + F。**

1. `todo` 加 `confirmed_at` / `confirmed_by`。**为空即未确认**，这是闸门的唯一判据。
2. 管理员的 `approve` 动作在**一个事务**里做四件事：写确认时间与确认人、状态推进到
   `in_progress`、追加一条 `kind='confirmation'` 的 `todo_step`、写一条 `todo.approved`
   的 outbox 事件。状态和 outbox 同事务，是为了不出现「确认了但主 agent 收不到放行信号」——
   而它此刻正被闸门挡着，收不到就等于这条 todo 静默死掉。
3. `approve` 幂等：已确认的再点，什么都不做，也不再发事件。
4. Agent 侧 `POST /api/agent/todos/{threadID}/state` 在 `confirmed_at IS NULL` 时拒绝
   `in_progress` / `awaiting_review` / `done`，返回 409 `todo_not_confirmed`，
   `retryable=false`（它需要人做一个动作，标成可重试只会让 agent 空转）。
   **`clarifying`、发帖、追加步骤都不受影响**——闸门挡的是「往下做」，不是「说话」。
5. `todo.approved` 定为 **P0**，和 `todo.assigned` 同档：它是主 agent 一直在等的放行信号，
   压在 P2 里排队等于让闸门白等一轮。同一次确认里关注者收到的是 `todo.status_changed`（P2）。
6. 新表 `todo_step`，seq 每条 todo 内从 1 递增。分配时**先锁 `todo` 行**再算
   `max(seq)+1`：不锁的话并发追加会读到同一个 max，唯一约束确实挡住了重复，
   但代价是一条步骤被吞掉。
7. `todo_step` **只有主 agent 能写**，关注者只读；`kind='confirmation'` 只由 hub 自己写。
   追加步骤**不产生 inbox 事件**——它是过程记录不是通知，每加一条就吵一次会把关注者的
   inbox 淹掉。
8. `reject` 收窄成「只用于 `awaiting_review` 打回」。确认之前它没有确定的目标状态：
   退回 `awaiting_response` 会抹掉已经发生的澄清对话，退回 `clarifying` 又和「不点确认」
   没有区别。确认之前管理员表达异议的方式是**发帖 + 暂不 approve**。

## 影响

- **Todo 模块**：多了一个人在环的必经步骤。M2 的出口标准要加上「admin 确认后 agent 才开工」。
- **Agent 侧 skill**：`agent-hub-skill` 要教 agent 这条流程——收到 `todo.assigned` 之后
  先问、先记 `clarification` 步骤，等 `todo.approved` 再动手；被 409 挡住时不要重试。
- **控制台**：todo 列表与详情要读 `confirmedAt`，为空时显眼地提示「等你确认」并给出确认按钮；
  详情页多一个「处理详情」时间轴。
- **升级**：`003_todo_confirmation_steps.sql` 跑完后**所有历史 todo 变成「待确认」**。
  这是刻意的——它们确实没有经过任何人的确认动作，按 status 回填等于第一天就给闸门开后门。
  代价是升级后管理员要把在办的 todo 逐条 approve 一次，一次性的。
- **审计**：多一条 `todo_approve`。重复 approve 不重复记——审计要能回答「这条是谁、
  什么时候放行的」，同一个答案记三遍只会让人以为放行过三次。

**什么情况下要重新审视这个决策**：如果出现「agent 自己发起 todo」（需求 §1 待定项之一），
闸门的确认人是谁就需要重新定义——目前 `confirmed_by` 存的是管理员的 subject，
默认「用户 = 唯一的那个管理员」。届时要么把闸门收窄成「只有 admin 建的 todo 才需要确认」，
要么给 `confirmed_by` 一个能表达 agent 身份的形态。
