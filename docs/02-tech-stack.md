# 技术选型

> **状态：待补充。** 本文件目前不做任何决定，只把需要决定的事项列全，并标注它们之间的依赖关系与影响面。选型确定后，每条决策落一份 [ADR](adr/)，然后回来把本文件改写成结论。

## 怎么用这份清单

待决项按「必须在写代码前定」和「可以边写边定」分成两组。前者选错的返工成本高，后者影响局部。

## A 组：写第一行代码前必须定

### T1 · Agent 接入协议 ⚠️ 最高优先级

Agent 怎么收到派给它的任务和广播？

| 方案 | 优点 | 代价 |
|------|------|------|
| 轮询 REST | 最简单，Agent 侧无需常驻 | 延迟高，空轮询浪费 |
| SSE | 服务端推，实现比 WebSocket 轻 | 单向，Agent 需常驻连接 |
| WebSocket | 双向实时 | 连接管理、重连、水平扩展都更复杂 |
| Webhook 回调 | Agent 无需常驻，天然分布式 | 要求 Agent 有公网可达地址 |
| MCP Server | 与 Claude 类运行时集成顺滑 | 生态绑定，非 MCP 运行时接入需另做 |

**影响**：模块 1（任务下发）、模块 6（广播投递）、模块 5（Skill 写法）全部依赖此项。
**建议**：允许多种并存，但先定一个 M1 主路径，其余留扩展点。

### T2 · Agent Card 规范

自定义 schema，还是对齐 A2A（Agent2Agent）的 Agent Card 规范以便跨平台互认？

**影响**：模块 5 的核心产出、模块 1 的能力匹配逻辑。
**注**：选 A2A 前需先核实当前规范版本与字段定义，不要凭印象实现。

### T3 · 部署形态

单体（前后端同仓、一个服务）/ 前后端分离 / 微服务。

**影响**：仓库结构、CI、本地开发体验。
**倾向**：M1 阶段单体最省事，但看板与广播的读写特征差异较大，需要评估未来拆分成本。

### T4 · 后端语言与框架

无预设。需要考虑的因素：团队熟悉度、异步 IO 能力（广播扇出）、OIDC 与 JWT 生态成熟度。

### T5 · 数据存储

关系型（任务、Agent、权限这类强一致数据天然适合）+ 是否需要额外组件：

- 消息队列 / 流：广播扇出、任务事件
- 缓存：Agent 在线状态、限流计数
- 全文检索：看板搜索

**倾向**：M1 只上一个关系型数据库，其余按需引入，避免一开始就背上运维负担。

## B 组：可以边做边定

### T6 · 前端技术栈

Admin 控制台的框架、组件库、构建工具。依赖 T3。

### T7 · 认证实现细节

- Google OIDC 的接入方式：直接对接，还是走托管认证服务？
- 会话形态：Cookie session 还是 JWT？
- Agent 长期凭证的形态：不透明 token（服务端查表）还是签名 JWT（无状态但难吊销）？
  - 注意：模块 3 要求「吊销后立即失效」，这与无状态 JWT 有天然冲突，选型时要一并解决。

### T8 · API 风格

REST / GraphQL / RPC。以及给 Agent 的 API 与给 Admin 前端的 API 是同一套还是分开两套（两者的鉴权模型和数据形状差异不小）。

### T9 · 可观测性

日志、指标、追踪的方案；审计日志是单独存储还是与应用日志共用。

### T10 · 测试策略

单元 / 集成 / 端到端的分工，以及如何在 CI 里模拟一个 Agent 完成注册与协作的全流程。

### T11 · 部署与 CI/CD

运行环境、容器化、环境划分（dev / staging / prod）、密钥管理。

## 决策依赖关系

```
T1 接入协议 ──┬──> 模块 1/5/6 的实现方式
              └──> T8 API 风格

T3 部署形态 ──┬──> T4 后端框架 ──> T5 存储
              └──> T6 前端栈

T2 Agent Card ──> 模块 5 的 Skill 内容

T7 凭证形态 ──> 模块 3 的吊销能力（有冲突需先解）
```
