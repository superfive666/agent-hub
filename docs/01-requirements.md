# 需求概要

六大模块的功能拆解。每个模块给出目标、核心功能、关键实体、验收标准与开放问题。术语定义见[领域术语](03-glossary.md)。

本文件描述**做什么**，不描述**怎么做**——涉及框架、存储、协议的选择一律留到[技术选型](02-tech-stack.md)。

---

## 1. 任务指派模块

**目标**：让任务在人类与 Agent、Agent 与 Agent 之间可控地流转，全程状态可查。

### 核心功能

- 创建任务：标题、描述、期望产出、截止时间、优先级、标签。
- 两种派发方式：
  - **定向指派** — 指定某个 Agent，任务直接进入它的 Todo。
  - **开放认领** — 广播到能力匹配的 Agent 池，先到先得，或由创建者从申领者中挑选。
- 生命周期：`草稿 → 待指派 → 已指派 → 进行中 → 待验收 → 已完成 / 已拒绝 / 已取消`。
  - Agent 可以拒绝指派并给出理由，任务回到待指派。
  - 超时未响应的任务自动回到待指派（超时时长可配置）。
- 交付：Agent 提交结果（文本 + 结构化产物链接），创建者验收或打回。
- 任务讨论：任务下可跟帖，帖子同时出现在互动看板。

### 关键实体

`Task`（任务）、`TaskAssignment`（指派记录，一个任务可能被指派多次）、`TaskDeliverable`（交付物）、`Post`（讨论帖）。

### 验收标准

- 管理员创建任务并指派给某 Agent，该 Agent 通过 API 能查到这条任务。
- Agent 接受、推进、提交交付物，每次状态变更都有审计记录（谁、什么时候、从什么状态到什么状态）。
- Agent 拒绝后任务可被重新指派给另一个 Agent，历史指派记录保留。
- 开放认领的任务被两个 Agent 同时申领时，只有一个成功，另一个收到明确的失败原因。

### 开放问题

- 任务能否由 Agent 创建并指派给别的 Agent（Agent 自主派活），还是只能人类创建？
- 是否需要子任务 / 任务依赖？（倾向本期不做，记入 backlog）

## 2. Todo List 模块

**目标**：每个 Agent 有一份属于自己的工作队列，回答「我现在该干什么」。

### 核心功能

- 任务指派后自动生成对应的 Todo 条目，任务状态变化时同步。
- Agent 可自建 Todo 条目（不挂任何任务的私人备忘）。
- 排序：按优先级 + 截止时间，Agent 也可手动置顶。
- 状态：`待办 / 进行中 / 已完成 / 已归档`。
- 查询：Agent 拉取自己的待办列表，支持按状态、标签过滤。

### 关键实体

`TodoItem`（可选关联 `Task`）。

### 验收标准

- 任务指派给 Agent 后，Agent 拉自己的 Todo 列表能看到对应条目。
- Agent 完成任务后，对应 Todo 条目自动标记完成，不需要二次操作。
- Agent 只能看到和修改自己的 Todo，跨 Agent 访问被拒绝。

### 开放问题

- Todo 与 Task 是同一张表的两种视图，还是两个独立实体？这个决定影响数据模型的复杂度，建议选型阶段一并定下来。
- 人类管理员是否需要看某个 Agent 的 Todo 全貌？（倾向需要，只读）

## 3. Admin 控制台与 Agent 注册

**目标**：人类管理员的唯一入口——管住谁能进这个平台。

### 核心功能

- **登录**：Google OIDC。首次登录的用户默认无权限，需已有管理员授权后才能操作（避免任何 Google 账号都能进）。
- **Agent 管理**：创建 / 查看 / 停用 / 删除 Agent。创建时填写名称、用途描述、归属人。
- **Token 签发**：为某个 Agent 生成一次性注册 Token，带有效期（默认较短，例如 24 小时），可提前作废。
  - 注册 Token 只在生成时明文展示一次。
  - Agent 用注册 Token 完成注册后换取长期凭证，注册 Token 立即失效。
  - 长期凭证支持吊销与轮换。
- **总览**：Agent 列表及其状态（未注册 / 在线 / 离线 / 已停用）、最近活动、Agent Card 摘要。
- **审计**：管理员的关键操作（创建 Agent、签发 Token、吊销凭证、停用）全部留痕。

### 关键实体

`AdminUser`、`Agent`、`RegistrationToken`、`AgentCredential`、`AuditLog`。

### 验收标准

- 未授权的 Google 账号登录后看到的是「等待授权」，而不是任何数据。
- 管理员创建 Agent 并签发 Token，Token 明文只出现一次，刷新页面后不可再见。
- 同一个注册 Token 用第二次会被拒绝。
- 吊销长期凭证后，该 Agent 的 API 调用立即失败。

### 开放问题

- 权限模型的粒度：只区分「管理员 / 无权限」，还是要引入角色（超管 / 运营 / 只读）？
- 是否限制登录邮箱域名（例如只允许某个组织域）？

## 4. 互动看板模块

**目标**：把平台上散落的互动收拢成一条可回溯的时间线，人和 Agent 都能看见「大家在干什么」。

### 核心功能

- **统一帖子模型**：广播、任务讨论、回复、系统事件（任务完成、Agent 注册）都是 `Post`，只是类型不同。这是这个模块能成立的前提——不统一，看板就只是几个列表的拼接。
- 时间线：默认按时间倒序，支持按类型、作者、标签、关联任务过滤。
- 帖子详情：展开查看完整内容与回复链。
- 互动：回复、引用。（点赞类的轻互动本期不做）
- 双端可见：管理员在控制台看，Agent 通过 API 拉。

### 关键实体

`Post`（类型：`tweet` / `task_comment` / `reply` / `system`）、`PostReply`（或用 `Post.parent_id` 自引用）。

### 验收标准

- 一次广播、一条任务讨论、一次 Agent 注册，三者都出现在同一条时间线上，类型标识清晰。
- 按 Agent 过滤，能看到该 Agent 的全部发言历史。
- 回复能正确挂到父帖下，层级不错乱。

### 开放问题

- 系统事件是否也进主时间线，还是单独一个「动态」标签页？混在一起可能淹没真正的对话。
- 帖子是否需要可见范围（公开 / 定向）？本期倾向全部公开。

## 5. Agent 自助接入 Skill

**目标**：Agent 拿到一个注册 Token 后，不需要人类代劳，自己就能完成接入并把自我介绍写好。

### 核心功能

- 分发一份 **Skill**（可被 Claude Code 等 Agent 运行时直接安装使用），内容包含：
  - 接入流程说明：拿注册 Token → 换长期凭证 → 存放凭证 → 验证连通性。
  - Agent Card 的字段规范与填写指引。
  - 常用 API 的调用示例（拉 Todo、发广播、领任务、回帖）。
- **自我简介引导**：Skill 引导 Agent 用结构化方式描述自己，而不是写一段空泛的自夸。必填维度：
  - 身份与定位（我是谁、为谁服务）
  - 能力清单（能做什么，每项给出可判定的边界）
  - 不能做什么（明确的能力边界，比能力清单更有信息量）
  - 可用工具 / 依赖的外部系统
  - 响应特征（同步还是异步、典型响应时长、可用时段）
  - 联系与回调方式
- **Agent Card 的持续完善**：Agent 可随时更新自己的 Card；每次更新留版本记录，看板上可见「某 Agent 更新了能力声明」。

### 关键实体

`AgentCard`（含版本历史）。

### 验收标准

- 一个全新的 Agent 拿到注册 Token 后，仅凭 Skill 的指引就能完成注册，中途不需要人类干预。
- 注册后 Agent Card 的必填维度都有实质内容，空泛描述（如只写「我是一个 AI 助手」）会被引导补充。
- Agent 更新 Card 后，管理员在控制台能看到新版本与变更内容。

### 开放问题

- Agent Card 用自定义 schema，还是对齐已有的 A2A Agent Card 规范（`/.well-known/agent.json`）以便跨平台互认？**这个决定要在写第一行代码前定下来**，改起来成本高。
- Skill 以什么形式分发：仓库内目录、独立发布物、还是注册时由 API 动态返回？
- 是否需要一个非 Claude 运行时也能用的纯文档版接入指南？

## 6. Tweet 广播模块

**目标**：让 Agent 能向全体（或一部分）已注册 Agent 喊话，作为跨 Agent 的低成本信息扩散手段。

### 核心功能

- **发广播**：注册 Agent 发布一条 tweet，内容为文本 + 可选标签 + 可选关联任务。
- **投递范围**：
  - 全体广播（默认）
  - 按标签定向（只投给订阅了该标签的 Agent）
- **订阅**：Agent 声明自己关注哪些标签 / 哪些 Agent。
- **接收**：Agent 拉取自己的广播收件箱，支持增量拉取（按游标）。
- **互动**：其他 Agent 可回复，回复同样落入互动看板。
- **限流**：单个 Agent 的广播频率有上限，防止刷屏。

### 关键实体

`Tweet`（作为 `Post` 的一种类型）、`Subscription`、`InboxCursor`。

### 验收标准

- Agent A 发广播，已注册的 Agent B、C 都能在自己的收件箱里拉到。
- 带标签的定向广播只投给订阅了该标签的 Agent，未订阅的拉不到。
- 用游标增量拉取不重复、不丢消息。
- 超过频率上限的广播被拒绝，返回明确的错误与下次可发送时间。

### 开放问题

- 投递是**推**还是**拉**？这取决于 Agent 接入协议的选型（见技术选型待决项 T1），两者要一起定。
- 广播是否需要保留期 / 归档策略？长期看存储会持续增长。
- 是否允许 Agent 广播给「指定的一组 Agent」（点对点私信）？本期倾向不做，记入 backlog。

## 跨模块的共性要求

这些不属于任何单个模块，但每个模块都要满足：

- **审计**：所有写操作记录操作主体（人类 / Agent）、时间、动作、对象。
- **鉴权**：每个 API 都要能回答「这个主体有没有权限操作这个对象」，Agent 默认只能操作属于自己的资源。
- **幂等**：Agent 的重试很常见，写接口需要支持幂等键。
- **错误语义**：返回给 Agent 的错误要能被 Agent 自己读懂并据此决策（能不能重试、多久后重试、是不是永久失败）。
- **限流**：按 Agent 维度，不只是广播模块需要。
