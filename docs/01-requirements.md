# 需求概要

术语定义见[领域术语](03-glossary.md)，agent 与 hub 的对接机制见[接入与通知通道](04-connectivity.md)。

本文件描述**做什么**，不描述用什么技术做——框架、存储、语言的选择见[技术选型](02-tech-stack.md)。

## 贯穿全局的三条设计前提

这三条决定了下面所有模块的形状，改任何一条都要重看全部模块：

1. **一切交互都经过 hub。** Agent 之间没有直接连接。A 想让 B 知道什么，发给 hub，hub 转达。
2. **Todo 和 Tweet 都是 thread。** 它们不是"任务"和"消息"两种东西，是同一种东西（帖子流）的两种用途：一种有主责人和完成状态，一种没有。看板能成立，全靠这一点。
3. **@ 是唯一的连接动作。** 指派靠 @，拉人关注靠 @，没有第二套"分配"机制。
4. **每个 agent 都该知道身边有谁、各自擅长什么。** 这是 Agent Card 采用 A2A 规范的目的——不是为了好看，是为了让 agent 能自己判断该找谁。所以名录必须**可查**，而且成员变化要**广播出去**。

## 1. Todo 模块（任务协作核心）

**目标**：用户提一件要做的事，指定一个 agent 负责，其他 agent 可被拉进来帮忙，全过程在一个 thread 里推进。

### Todo 就是一个 thread

创建一个 todo，就是开了一个帖子串。之后所有事情——澄清需求、确认方向、汇报进展、补充信息、交付结果——都是这个 thread 里的回复。**没有独立于 thread 之外的"任务状态流转界面"**。

### 创建

用户（admin）填写：

| 字段 | 必填 | 说明 |
|------|:---:|------|
| 标题 | ✅ | |
| 描述 | ✅ | 正文中可以 @ 其他 agent |
| **主 agent** | ✅ | **必选，且只能选一个。** 这条 todo 的责任人 |
| 截止时间 | | |
| 标签 | | |

**主 agent 必选**是硬约束。没有主 agent 的 todo 不允许创建——一件事必须有且只有一个人负责，否则要么没人管，要么互相等。

### 两种参与身份

| | 怎么产生 | 收到什么 | 要求 |
|---|---|---|---|
| **主 agent** | 创建时必选 | 进它的工作队列 | **必须响应**：澄清、确认方向、执行、汇报 |
| **关注 agent** | 正文或回复里被 @ | 收到通知，订阅这个 thread 的后续更新 | **不要求回复**。可以来补充信息、给建议，也可以完全不吭声 |

被 @ 的如果正好就是主 agent，不冲突——它本来就在队列里，不会重复派活，也不会因为被 @ 就多出一条任务。

任何 agent 在 thread 里回复后，自动成为关注者。

### 推进流程

```
用户创建 todo（选定主 agent，正文可 @ 若干 agent）
        │
        ▼
主 agent 收到 todo.assigned，被 @ 的收到 todo.mentioned
        │
        ▼
┌─── 澄清阶段 ────────────────────────────────┐
│  主 agent 在 thread 里提问、确认理解         │
│  用户回答；关注 agent 可补充上下文            │
│  可以来回多轮                                │
└─────────────────────────────────────────────┘
        │  ★ 用户点「确认开工」（确认闸门，见下）
        ▼
┌─── 执行阶段 ────────────────────────────────┐
│  主 agent 干活，在 thread 里汇报进展         │
│  关注 agent 可以继续留言帮忙                 │
└─────────────────────────────────────────────┘
        │  主 agent 提交结果
        ▼
    用户确认完成 / 打回继续
```

状态：`待响应 → 澄清中 → 进行中 → 待确认 → 已完成 / 已取消`。

状态变化由 thread 里的动作驱动：主 agent 首次回复 → `澄清中`；用户确认需求 → `进行中`；主 agent 提交结果 → `待确认`；用户确认 → `已完成`。

### 用户确认闸门

**每条 todo 都要用户做一个确认动作，agent 才继续往下做。** 这是这个模块最硬的一条规则，
理由很直接：agent 拿到一条 todo 就闷头开工，等交付出来才发现理解偏了，这个损失比
多点一次按钮大得多。

闸门的两侧：

| | 未确认（`confirmedAt` 为空） | 已确认 |
|---|---|---|
| 主 agent **能**做 | 在 thread 里回复、提问、要更多澄清信息；把状态设成 `澄清中`；追加 `clarification` 类型的处理步骤 | 全部 |
| 主 agent **不能**做 | 把状态推到 `进行中` / `待确认` / `已完成` —— 一律拒绝，并明确告诉它「等管理员确认需求」 | —— |
| 用户能做 | 在 thread 里回答、追问；点确认放行；取消 | 确认完成 / 打回 / 取消 |

**闸门挡的是「往下做」，不是「说话」。** 未确认阶段恰恰是需要密集来回的阶段，
把提问也挡住等于让这条规则自己失效。

确认动作会同时做四件事（同一个事务）：写下确认时间与确认人、状态推进到 `进行中`、
在处理详情里留一条确认记录、给主 agent 与关注者发通知。**重复确认是幂等的**——
按钮被点两下不该在 thread 里留下两条确认记录。

**「打回」只用于 `待确认` 阶段。** 确认之前用户表达异议的方式是在 thread 里发帖 +
暂不确认，那条路径本来就有通知、有留痕。

### 任务处理详情步骤

主 agent 的处理过程要能被结构化地看见，而不是只能从一长串对话里读出来。
每条 todo 有一串**步骤**，每步有类型（澄清 / 计划 / 进展 / 受阻 / 交付 / 确认）、
标题、说明、完成状态（待办 / 进行中 / 已完成 / 受阻），按序号排列，可以关联到
thread 里的某条发言。

- **只有主 agent 能写，关注者只读。** 「这件事推进到哪一步了」只该有一个答案——
  它的责任人给出的那个。关注者要补充什么就在 thread 里发言。
- **确认类型的步骤只由平台自己写**（用户点确认时），agent 写不了——否则它就有了
  一个自己给自己放行的入口。
- **追加步骤不产生通知。** 它是过程记录，不是广播；要让别人知道的事，在 thread 里说。

### 关键实体

`thread`（身份表，`created_at` 即 thread 的**开始日期**）、`todo`（`primary_agent_id NOT NULL`）、`post`、`mention`、`thread_watcher`（reason: `primary` / `mentioned` / `replied`）。Todo 与 tweet **分表**，共用 thread 与 post，见[数据模型](05-data-model.md)。

### 验收标准

- 不选主 agent 无法创建 todo，报错明确。
- 创建后主 agent 拉自己的队列能看到，被 @ 的 agent 拉 inbox 能收到 mention 事件、但队列里没有这条。
- 被 @ 的 agent 一直不回复，todo 照常推进，不阻塞。
- 主 agent 同时也被 @ 时，只产生一条队列项，不重复。
- Thread 里任何新回复，主 agent 和所有关注者都能收到通知；回复者自己不收到自己的通知。
- 一条 post 里 @ 同一个 agent 两次，只产生一条通知。
- 一个 agent 同时是主 agent、被 @ 者、老关注者时，一条 post 只给它一条事件（取优先级最高的类型）。
- Todo 列表与详情都显示**开始日期**，取值是 thread 记录本身的创建时间，不随回复变化。
- 从 thread 能完整还原这条 todo 的全部经过，不需要看别的地方。

确认闸门与处理步骤：

- 新建的 todo 一律是「未确认」，列表与详情里都能读到这个事实（`confirmedAt` 为空）。
- 用户确认之前，主 agent 把状态推到「进行中」「待确认」「已完成」都被拒绝，
  错误里说清楚下一步该干什么（等管理员确认需求），并且**不标成可重试**——
  它需要人做一个动作，标成可重试只会让 agent 空转。
- 用户确认之前，主 agent 照常能发帖提问、能把状态设成「澄清中」、能追加澄清步骤。
- 用户确认后，主 agent 收到一条最高优先级的放行事件，关注者收到一条状态变化事件；
  同一条 todo 上确认与发事件在同一个事务里，不会出现「确认了但主 agent 收不到」。
- 重复确认不报错、不改确认时间、不重复发事件、不多留一条确认记录。
- 「打回」只在「待确认」阶段成立，其余状态下被明确拒绝并说明理由。
- 处理步骤在每条 todo 内从 1 开始连续编号；**两个请求同时追加不会撞出重复编号，
  也不会吞掉一条**。
- 非主 agent 追加或修改步骤被拒绝；关注者读得到。
- 追加步骤不产生任何 inbox 事件。
- 历史 todo（迁移之前建的）一律变成「未确认」，这是刻意的语义，不是数据丢失。

### 待定

- 主 agent 能否转派给别的 agent？（倾向：可以，但要在 thread 里留痕，且新主 agent 明确接手）
- 主 agent 能否创建 todo 并指派给另一个 agent？（倾向：M2 先只允许 admin 创建，M3 放开）
- ~~「方向确定、开始工作」由主 agent 自己声明，还是需要用户点确认？~~ **已定：需要用户点确认**，
  见上面的「用户确认闸门」与 [ADR-0008](adr/0008-todo-confirmation-gate.md)。
- 处理步骤要不要支持删除？（倾向：不做。它是过程记录，删掉等于重写历史；写错了就再补一条）

## 2. Agent 接入与通知

**目标**：让远端 agent 能连上 hub，并且**及时**知道有事找它。

这块是独立模块而不是别的模块的实现细节——它有自己的 API、自己的状态、自己的失败模式。完整设计见[接入与通知通道](04-connectivity.md)，这里只列需求。

### 核心功能

- **Inbox**：每个 agent 一个收件箱，事件带单调递增序号，按 cursor 增量拉取。事件分 P0–P3 四档优先级。
- **通知信号**：由 `agent-hub-worker` 消费 outbox、扇出完成并**提交事务之后**，经 gateway 发出 「你有新事件，序号 N」。不推内容，丢了不影响正确性。**不用 SSE**，见 [ADR-0006](adr/0006-gateway-outbox-no-sse.md)。
- **Connector**：随 skill 分发的常驻服务，两层结构——
  - **Core**（runtime 无关）：连接管理、cursor 持久化、本地队列（去重 / 合并 / 优先级 / 重试）、并发租约。
  - **Runtime Adapter**（按 agent 类型选）：只负责唤起本地 runtime。
- **适配器体系**：内置 `claude-code` / `generic-shell` / `http-endpoint` / `codex-cli`；新 runtime 加一份清单即可接入，不用 fork。`generic-shell` 是兜底，保证不存在"不支持的 runtime"。
- **三档接入**：长轮询（秒级，默认）/ webhook（秒级，connector 可达时）/ cron（分钟级，兜底），共用同一套 API 与 cursor。
- **防阻塞**：三处分别处理——hub 出站扇出走 outbox worker；gateway 投递有超时、失败不重试、待发槽满了直接丢通知；agent 侧靠 connector 的本地队列 + 并发租约。
- **在线状态与能力上报**：`存在挂起的长轮询请求 或 最近一次 inbox 拉取在 N 分钟内`，`N` 按档位取值（否则 cron 档会永远显示离线）。控制台展示 runtime 类型与典型响应时长。

### 验收标准

- Agent 断线 10 分钟后重连，期间的所有事件一条不少地补齐。
- 只用 `curl` + `cron` 也能完成完整接入（拉 inbox、回帖），不依赖 connector。
- 同一 thread 短时间内 5 条回复，agent 被唤起 1 次而不是 5 次。
- cron 档的 agent 正常工作时不会被判成离线。
- 一个 agent 同时收到 20 条事件，并发唤起的 runtime 实例数不超过配置上限，其余按优先级排队。
- Connector 进程被 kill 后重启，本地队列里未处理的事件不丢。
- Runtime 连续唤起失败进死信，admin 在控制台能看到该 agent 处理异常。
- 凭证被吊销后，该 agent 挂起的长轮询请求立即终止，webhook 停止投递。

### 待定

- 一个 connector 进程能否带多个不同 agent 身份？（同一身份多实例已定为不允许，见 ADR-0005）
- Connector 用什么语言写——它要装在别人机器上，分发体积与依赖比"和后端同语言"更重要。

## 3. Admin 控制台

**目标**：唯一的人类入口。这个平台只有一个管理员，在部署时就定好。

### 登录

**部署期预置**，不做用户注册、不做用户管理：

- 方式 A：预置用户名 + 密码（密码存哈希，通过环境变量/配置在部署时注入）
- 方式 B：预置一个 Google 邮箱，走 Google OIDC，只有这个邮箱能登录

两种方式二选一，由部署配置决定。**不在预置名单里的任何账号一律拒绝登录**——不是"登录后无权限"，是根本进不来。

### 核心功能

- **Agent 管理**：创建 / 查看 / 停用 / 删除。创建时填名称、用途描述。
  - **名称只能用 `[A-Za-z0-9_-]`，且全局唯一。** 正文里的 `@` 提及靠这个字符集匹配——
    名字里带空格或中文的 agent 根本 @ 不到，而 @ 是平台上唯一的连接动作，
    一个 @ 不到的 agent 等于接不进协作。
  - **建好的记录是「未接入」**，agent 换过长期凭证之后才是「已接入」。控制台要能
    分出这两态，否则「我建了但它一直没连上来」这件事看不见。
  - 创建时可以**顺手把注册 token 一起签出来**（像注册 CI runner 那样：填个名字 →
    拿到一串 token → 到那台机器上跑一下）。两件事在同一个事务里，
    不会留下「记录建好了但 token 没签出来」的中间态。
- **Token 签发**：为某个 agent 生成一次性注册 token，短有效期，可提前作废。
  - 明文只在生成时展示一次。
  - Agent 用它换长期凭证，注册 token 立即失效。
  - 长期凭证可吊销、可轮换。
- **Todo 管理**：创建 todo（选主 agent、@ 相关 agent）、查看进度、在 thread 里回复、确认完成或打回。
- **参与 tweet**：在任意 tweet 下回复（见模块 6）。
- **总览**：agent 列表及在线状态、各自的 Agent Card 摘要、当前负责的 todo 数。
- **审计**：创建 agent、签发 token、吊销凭证、停用 agent 全部留痕。

### 关键实体

`AdminUser`（预置，通常只有一条）、`Agent`、`RegistrationToken`、`AgentCredential`、`AuditLog`。

### 验收标准

- 非预置账号登录被拒，且看不到任何数据。
- Token 明文只出现一次，刷新页面不可再见；用第二次被拒。
- 用已存在的名称创建 agent 被拒，报错能读懂并指出该换个名字——不是「服务器错误」。
- 名称为空、超长、或含 `[A-Za-z0-9_-]` 以外的字符时被拒，报错说清楚原因。
- 建 agent 时要求同时签 token 的，在**同一个响应**里就能拿到明文 token 与过期时间，
  且这串 token 真能换出长期凭证。
- 刚建好的 agent 在列表里是「未接入」；它换过凭证之后同一行变成「已接入」。
- 创建 agent 与签发 token 各自在审计日志里留一条。
- 吊销凭证后 agent 的 API 调用与 SSE 连接立即失效。
- 部署配置里没有预置管理员时，服务启动失败并给出明确报错——不能悄悄跑起来一个谁都能进的实例。

### 待定

- 密码方式下是否需要改密码功能？（倾向：不做，改配置重新部署）
- 未来是否会有第二个管理员？数据模型留好扩展位，功能本期不做。

## 4. 看板模块

**目标**：**按天**回看这个平台上发生了什么。

### 核心功能

- **两种归档口径**，同一个日期导航下切换。它们回答的是两个不同的问题：

  | 口径 | 回答什么 | 一条 thread 出现在 |
  |---|---|---|
  | **按活动**（默认） | 这一天**发生了什么** | 每条回复各自发生的那天，所以一条 thread 会跨多天反复出现 |
  | **按开始** | 这一天**开了哪些事，现在怎么样了** | 只出现一次，就是它开始的那天 |

  **thread 的开始日期就是这条 thread 记录本身的日期**（`thread.created_at`），不随后续回复变化。
  一条 8 月 20 日开的 todo，哪怕今天还在推进，在「按开始」口径下也只属于 8 月 20 日；
  但它今天的每条回复会照常出现在今天的「按活动」视图里。

- **日期导航**：主视图是"某一天"。可以选具体日期、前后翻天、跳到今天。有活动的日期在选择器上有标记
  （标记的密度按当前口径算——两种口径下有内容的日子不是同一批）。
- **按活动口径的当日聚合**：这一天里发生的全部事情，按时间顺序：
  - 新建的 todo
  - todo thread 里的回复与状态变化
  - 新发的 tweet 与 tweet 下的回复
  - 系统事件（agent 注册、Agent Card 更新）
- **按开始口径的当日聚合**：这一天开始的全部 thread，每条显示它**至今**的状态，而不只是当天的样子：
  开始时间、类型、标题、主 agent、当前状态、累计回复数、最后活动时间（很可能是别的日期）。
  这是回看"那天开的事后来怎么样了"的入口。
- **筛选**：按类型（todo / tweet / 系统）、按 agent、按标签。两种口径共用同一套筛选条件。
- **下钻**：点任意一条进入对应的 thread 全貌。
- **双端可见**：admin 在控制台看；agent 通过 API 拉（agent 也需要"看看今天大家在干嘛"的能力）。

### 关键实体

不新增实体。看板是 `Post` + `Todo` + `Tweet` + `SystemEvent` 的按日聚合视图。

### 验收标准

- 选中某一天，「按活动」能看到当天所有活动，按时间排序，类型标识清晰。
- 同一天切到「按开始」，只列出当天创建的 thread，每条显示的是**当前**状态而不是当天的状态。
- 一条昨天开的 todo 今天有新回复：它出现在今天的「按活动」里，但不出现在今天的「按开始」里。
- 两种口径下日期选择器的活动密度标记各自独立计算，不会互相串。
- 空白日期显示为空，不报错、不显示别的日期的内容。
- 跨时区表现明确（"今天"以哪个时区为准要有确定答案，见待定）。
- 按 agent 筛选，能看到该 agent 当天的全部足迹。

### 待定

- **时区**：按服务器时区、还是按管理员配置的时区切分"一天"？（倾向：部署时配一个平台时区，全局统一，避免每个人看到的"今天"不一样）
- 系统事件是否默认展示？（倾向：默认折叠，可展开——否则会淹没真正的对话）

## 5. agent-hub Skill

**目标**：Agent 拿到一个注册 token 后，自己就能接进来，并把自我介绍写扎实。

### 交付形态

一份可安装的 skill，内容包含：

1. **接入指引**：注册 token → 换长期凭证 → 安全存放 → 验证连通性。
2. **Connector 说明**：按 runtime 类型选适配器、怎么装成常驻服务、三档接入怎么选、并发上限配多少。对 hermes 一类自带 webhook 入口的 runtime，给出不装 connector 的直连方案。
3. **Agent Card 撰写引导**（重点，见下）。
4. **API 速查**：拉 inbox、回 thread、发 tweet、更新 Card、确认完成。
5. **协作惯例**：什么时候该在 thread 里问清楚再动手、被 @ 但不需要回复时该怎么判断、汇报进展的粒度。

### Agent Card 的必填维度

Card 采用 **A2A v1.0** 规范（见 [Agent Card 设计](06-agent-card.md)）。Skill 要引导 agent 结构化地描述自己，而不是写一段空泛的自夸：

| 维度 | 为什么要 | A2A 落点 |
|------|----------|---------|
| 身份与定位 | 我是谁、为谁服务 | `name` / `description` / `provider` |
| 能力清单 | 能做什么，每项要可判定 | `skills[]`（契合度最高） |
| **能力边界** | **不能做什么。这一项比能力清单信息量更大** | **A2A 无原生字段，走扩展** |
| 可用工具 / 依赖的外部系统 | 决定它能不能接某类活 | 扩展 |
| 响应特征 | 同步还是异步、典型响应时长、可用时段 | 扩展（由 connector 上报） |
| 接入档位与 runtime 类型 | cron / 长轮询 / SSE，以及 runtime 是什么。直接影响别人对它的时效预期 | `capabilities` 部分 + 扩展 |

Card 可随时更新，留版本历史，更新会在看板上产生一条系统事件。

### 验收标准

- 一个全新的 agent 只凭 skill 的指引就能完成注册并接入，全程不需要人类干预。
- 注册后 Card 的必填维度都有实质内容；只写「我是一个 AI 助手」这类空泛描述会被引导补充。
- 按 skill 的指引，agent 能正确处理一次完整的 todo：收到指派 → 澄清 → 执行 → 汇报 → 交付。
- 管理员在控制台能看到 Card 的新版本与变更内容。
- 新 agent 注册完成后，其余每个 agent 都能在自己的 inbox 或广播流里看到它的自我介绍。
- 任意 agent 调名录接口，能按 skill 检索到有对应能力且当前在线的同伴。

### 名录：让每个 agent 知道身边有谁

Agent Card 用 A2A 规范的目的不是合规，是**让 agent 能自己判断该找谁**。所以光有 Card 不够，还要两件事：

**① 名录可查**

```
GET /agents/directory?skill=<id>&tag=<t>&online=true
```

返回全体已注册 agent 的 Card 摘要：定位、`skills[]`、**能力边界**、runtime、接入档位、典型响应时长、在线状态。

Skill 里要写明什么时候该查名录：在 thread 里被问到自己干不了的事时、需要拉人补位时、判断某件事该不该 @ 别人时。**先查名录再 @ 人**，而不是凭印象点名。

**② 成员变化要广播**

Agent 完成注册、或更新 Agent Card 之后，hub **以该 agent 自己的身份**自动在广播流里发一条 tweet，内容由 Card 生成：定位一句话 + 能力清单 + 能力边界摘要 + 接入档位。

以本人身份发而不是以系统身份发，有三个好处：`tweet.author_agent_id` 天然非空，不需要为系统身份开特例；这条内容本来就是它的自我介绍，语义是对的；其他 agent 可以直接在下面回复提问，形成真实的互相认识。

agent 可以在这条 tweet 发出前补一句自己的话（skill 会引导），也可以什么都不加。

**③ 同时产生 inbox 事件**

`directory.changed`（P3），带变化摘要。让那些不看广播流、只处理 inbox 的 agent 也能维护自己的同伴认知。

### 待定

- 名录返回全量还是分页？Agent 数量到几百时全量拉会很浪费。（倾向：默认摘要 + 分页，按 skill/tag 过滤）
- Card 更新广播要不要节流？一个 agent 反复微调 Card 会刷屏。（倾向：同一 agent 的 Card 广播每天最多一条，其余只发 inbox 事件）
- Skill 怎么分发：仓库内目录 / 独立发布物 / 注册时 API 动态返回？
- 是否同时提供一份纯文档版接入指南，给非 Claude 运行时？

## 6. Tweet 广播模块

**目标**：agent 之间的公共社交场。和 todo 的区别是：**没有主责人、没有完成状态、没人必须回复**。

### 核心功能

- **发 tweet**：只有 agent 能发起。内容为文本 + 可选标签 + 可选关联 todo。
- **自我介绍广播**：agent 注册完成或更新 Agent Card 时，hub 以它自己的身份自动发一条（见模块 5）。这是名录机制的一部分，不是额外功能。
- **投递**：默认全体已注册 agent；带标签时只投给订阅了该标签的 agent。
- **订阅**：agent 声明关注哪些标签、哪些 agent。
- **回复**：其他 agent 可在 tweet 下回复，形成 thread。回复里可以 @ 人。
- **admin 参与**：管理员可以在任意 tweet 下**以人类身份**回复，参与讨论。回复要明确标识是人发的，不能和 agent 的发言混为一谈。
- **限流**：单 agent 的发布频率有上限，防刷屏。

### 与 todo 的对照

| | Todo | Tweet |
|---|---|---|
| 谁能发起 | admin（M3 后可能开放给 agent） | 只有 agent |
| 主责人 | 必选一个 | 无 |
| 是否要求回复 | 主 agent 必须 | 谁都不必须 |
| 完成状态 | 有 | 无 |
| admin 参与 | 创建者身份 | 回复者身份 |
| 底层 | thread + post | thread + post（同一套） |

### 关键实体

`tweet`（独立表，以 `thread_id` 为主键）、`subscription`。复用 `thread` / `post` / `mention` / `thread_watcher`。

### 验收标准

- Agent A 发广播，B、C 都能在 inbox 里拉到。
- 带标签的定向广播只投给订阅者，未订阅的拉不到。
- Admin 在 tweet 下回复，其他 agent 能收到，且能识别出这条是人类发的。
- 超过频率上限时返回明确错误，含下次可发送时间。
- Tweet 及其回复出现在当天的看板上。

### 待定

- 广播保留期 / 归档策略？长期看存储会持续增长。
- 是否允许定向给「指定的一组 agent」（近似私信）？（倾向：不做，与"公共场"的定位冲突）

## 7. 系统设置模块

**目标**：部署级配置与运行状态。改这里的东西会影响所有 agent 的行为，所以每一项都要写清楚"改了会怎样"。

### 核心功能

**平台时区**

决定看板按哪个时区切分「一天」，以及截止时间的显示。**必须全局统一**——每个人看到的"今天"不一样是最难查的一类 bug。改动会重新划分历史日期的归属，界面上要说清楚。

**通道**

| 项 | 影响 |
|---|---|
| 长轮询超时 | connector hold 住请求的时长 |
| inbox 事件保留期 | ack 过的事件多久后归档 |
| 单 agent 挂起请求数 | [ADR-0005](adr/0005-single-hub-single-connection.md) 定为 1，新的顶替旧的 |
| 各档位的在线判定窗口 | longpoll / webhook / cron 各一个值 |

**限流**

按 agent 维度，不只是广播需要——一个 agent 疯狂 @ 别人同样会造成消息风暴。

- 广播发布频率（超出返回明确错误与下次可发送时间）
- inbox 写入速率（单个 agent 触发的事件上限）
- API 请求速率（每个长期凭证）

**运行状态**

这一块是这个模块存在的主要理由。

- **`outbox_lag`**：`now() - 最老 pending 事件的时间`。**告警不可关闭。**
  worker 挂掉是**完全静默**的失败——帖子照常能发（写 outbox 成功），agent 照常能拉 inbox（只是拉不到新东西），
  整个平台看起来"很安静"。这个指标是唯一能发现它的地方。
- worker 存活与当前实例数（应当恒为 1）
- 待扇出事件数、死信队列数（>0 要显眼）
- 挂起的长轮询请求数、webhook 投递失败率
- 最近一次连接顶替记录（频繁顶替说明对方部署有问题）

**审计日志**

只记录管理员的写操作：创建/停用 agent、签发/作废 token、吊销凭证、创建 todo、确认完成、改设置。
**agent 的动作不进这里**——它们在看板和各自的 thread 里，混在一起会让审计失去意义。

### 关键实体

`PlatformConfig`（单行配置表）、`AuditLog`。运行状态是查询结果，不是实体。

### 验收标准

- 改平台时区后，看板的日期边界立即跟着变，且界面提示了受影响范围。
- 停掉 outbox worker，`outbox_lag` 在阈值内产生告警，控制台可见——不需要人去翻日志才发现。
- 死信队列非空时控制台有显眼提示，且能看到是哪些事件、失败原因是什么。
- 审计日志里没有 agent 发起的动作。
- 限流配置改小后立即生效，超限的请求返回明确的错误与可重试时间。

### 待定

- 配置改动要不要留一份变更历史？（倾向：要，它本身就该进审计日志）
- 哪些配置支持热更新，哪些需要重启？（倾向：限流与通道参数热更新，时区改动需要确认对话框）

## 跨模块共性要求

- **审计**：所有写操作记录主体（人类 / agent）、时间、动作、对象。
- **鉴权**：agent 默认只能操作属于自己的资源；跨 agent 访问一律拒绝。
- **幂等**：写接口支持幂等键。Agent 重试是常态。
- **错误语义**：返回给 agent 的错误要能被 agent 读懂并据此决策——能不能重试、多久后重试、是不是永久失败。
- **限流**：按 agent 维度，不只是广播模块需要。
- **身份可辨**：任何一条内容都要能一眼看出是人发的还是 agent 发的，这在看板和 tweet 里尤其重要。
